# D-037 · 문서 목록은 우리 시스템에서 뽑는다 — 골격 유지·파일 2건 신설, 세션 운영 규칙 2건 (2026-08-04 · D-036 논거 정정·보강)

> [ADR 인덱스](README.md) · 결정 ID: D-037

- **결정**: 외부 하네스의 **디렉터리 골격(`references`·`checklists`·`adr` + 역할 문서)은 이미 채택했고 그대로 둔다.** 그러나 **파일 목록 27개를 그대로 채우지는 않는다** — 우리 코드·운영에서 실제로 뽑히는 것만 만든다. ① 신설 2건: [`references/coding-conventions.md`](../references/coding-conventions.md)(패키지 배치·네이밍·`create`/`restore`/`of`·`Clock` 주입·테스트 3층·Lombok 사용 범위), [`references/observability.md`](../references/observability.md)(`[measure]` 로그 규약·계측 위치·현재 없는 것). ② `workflows/`·`prompts/`는 만들지 않는다 — 각각 HARNESS §0.7·`roles/`와 중복(D-023). `workflows/`는 배포를 시작해 `deployment`·`rollback`·`release-note`가 **동시에** 내용을 갖는 시점에 생긴다. ③ 세션 운영 규칙 2건을 HARNESS §0.8에 추가: **이슈 1개 = 구현 세션 1개**(끝나면 세션을 버린다), **병렬화(`/team`·서브에이전트)는 👀 검수에서 기본 / 🔧 구현은 기계적 반복에만**.
- **이유**: 27개 파일을 하나씩 실사한 결과 — **지금 쓸 내용이 있는 것 3** · 이동·개명이면 되는 것 3 · **이미 원본이 있어 만들면 D-023 위반인 것 5**(`architecture`=CLAUDE.md+MVP-DESIGN, `development`=HARNESS, `database-design`=MVP-DESIGN ERD, `team-configuration`=`roles/`, `code-review`=REVIEWER.md) · **내용이 전무한 것 12** · 부분 2. 특히 `api-design.md`는 **컨트롤러가 0개**(배치 시스템이라 REST API 자체가 없다), `security*`는 보안 의존성 0건이다. 저 27개는 그 회사가 *실제로 가진 것*의 목록이므로, 베끼면 **남의 시스템의 형태를 우리 시스템의 문서로 주장**하게 된다 — D-036이 최악의 흠으로 지목한 "존재하지 않는 `.claude/skills/`를 광고하는 README"와 같은 종류의 거짓이다. 반대로 신설 2건은 근거가 코드에 있다: 테스트 37개가 `AbstractIntegrationTest`·`TestContainerImages`·Fake 포트 직접 구현(**Mockito import 0건**)·AssertJ(35파일)로 수렴해 있는데 문서에 한 줄도 없어, 세션이 갈릴 때마다 코드에서 역추론하고 서로 다른 결론에 도달할 여지가 있었다.
- **보강 — 서브에이전트 권한 상속 실증 (2026-08-04)**: 「조율 세션 하나만 띄우고 그 안에서 `/team`으로 병렬 처리」안을 검토해 **기각**했다. 검수 프로파일(`Edit(sift-api/**)` deny)로 헤드리스 세션을 띄워 **서브에이전트를 통해** `sift-api/README.md` 편집을 시도하니 `File is in a directory that is denied by your permission settings.`로 차단됐다(파일 미변경 확인). 즉 **권한 경계는 세션 단위이고 서브에이전트가 우회할 수 없다.** 따라서 단일 세션 + 서브에이전트로는 역할 분리를 대체할 수 없다 — 부모가 코드를 못 쓰면 자식도 못 쓰고, 부모 권한을 풀면 경계 자체가 사라진다(D-034 폐기). 이 상속은 반대로 **장점**이기도 하다: 각 역할 세션 안에서 병렬화해도 경계가 공짜로 유지된다.
- **비고 — D-036의 두 논거 정정**: ① D-036에서 「저 구조는 단일 세션용 *작업 축* 라우팅이라 *역할 축* 멀티세션과 안 맞는다」고 적은 것은 **틀렸다.** 두 축은 직교하므로 겹쳐 쓸 수 있고, 세션이 냉시작하는 멀티세션에서 작업 축 로딩은 오히려 더 값어치가 있다. 진짜 기각 사유는 축이 아니라 **가리킬 문서가 없다**는 것이다 — 트리거는 문서가 있어야 성립하는 인덱스다. 그래서 이번에도 트리거 표를 만들지 않았다: 규약 문서가 2개째 필요해질 때(원칙 2) 만든다. ② 「한 이슈는 보통 파일 몇 개」라고 한 것도 **틀렸다** — 병합 PR 21개 실측 결과 **중앙값 약 13파일, 최대 35파일**(#26)이다. 구현에서 병렬화를 쓰지 않는 이유는 파일 수가 아니라 **의존 체인**(도메인→포트→서비스→어댑터→테스트)과 **워킹 트리 공유**(브랜치는 워커가 아니라 디렉터리의 속성)다. 워커별 브랜치 분리는 git worktree가 필요한데, OMC `/team`의 worktree 모드는 opt-in이고 우리 워크스페이스 루트가 git이 아니라(D-015) 동작 여부를 **확인하지 않았다** — 필요가 실측되면 그때 검증한다.
